# ShareK for macOS

Menu bar screenshot, recording and annotation app. Swift 6 + AppKit, SwiftPM only (no Xcode project), `Package.swift` targets macOS 15. Footprint budget: the menu bar process idles at ~8 MB and 0% CPU; the editor process lives only while it has a window, and keeps the pixels of its captures and the frame it shows in temp files, not in memory, so it stays near 20 MB whatever the window size or the number of tabs. No cloud or upload features. It builds only on the Mac that runs it; no binary, tag or release workflow is ever published.

## Build & run

- `scripts/build.sh` → `build/ShareK.app` (release build, `Resources/Info.plist`, `assets/icon/AppIcon.icns`), signed with the self-signed `Nico Local` identity when the keychain has it, else ad-hoc.
- `scripts/install.sh` builds, quits the running app (`scripts/quit.sh` posts the `local.sharek.quit` distributed notification, then `pkill`), copies the bundle to `~/Applications/ShareK.app`, registers it with LaunchServices and opens it. `scripts/uninstall.sh` quits and removes it.
- `scripts/test.sh` runs `swift test` with the Swift Testing plugin path the Command Line Tools need. `Tests/ShareKTests` covers `RegionLabel`, `ScrollStitcher`, the icon paths and colors, `Pixels.blit`, `SoftShadow`, the tab shown after one closes and `MappedFrame`.
- `scripts/memory-check.py <binary> <out>` measures the editor with nobody at the keyboard: it starts `ShareK --editor`, speaks the IPC protocol to it, opens four synthetic 6016×3384 captures and drives it through `EditorProbe` (resize the window and render at 2×, switch tabs directly and by a click on the tab bar, draw shapes, pin the capture, zoom, minimize, close tabs), reading `footprint` after each step and sampling it in between for the peak. It fails when a step leaves the editor in another state than the one it asked for, when the frame is not a mapped one or when the editor runs without `MallocSpaceEfficient`. It also checks that undo still works after leaving a tab and coming back, that a tab keeps its zoom, and that a recording opens as a tab. A second editor gets its window set to another color space (`untag`) and must fall back to IOSurface frames, and the menu bar process is opened last through LaunchServices, as Finder and the login item open it, and measured idle; it fails when that process runs without `MallocSpaceEfficient` or AppKit logs a failed status item. It writes `memoria.txt`, PNGs of the frames the overlay showed and screenshots. `CHECK_PROFILE=true` adds a pass under `MallocStackLogging` that lists what allocated the memory of the editor and of the menu bar process. `.github/workflows/macos.yml` runs it on a GitHub Mac after building and testing; `gh workflow run macos.yml --ref <branch> -f patch="$(git diff --binary HEAD | gzip | base64 -w0)"` does the same for uncommitted changes, with new files first marked by `git add -N`, and `-f profile=true` adds the profile. The runner has no one producing events, and AppKit frees a closed window only at the next event, so the probe posts one after every command.
- `scripts/memory-report.sh` is the same measurement by hand on this Mac: it relaunches ShareK, asks for seven actions (one capture, three tabs, a fourth capture, a tab switch, a drawing, minimize, close three tabs) and after each one records `footprint`, `vmmap` and `heap`; a loop samples `footprint` every 0.2 s for each step's peak, `sample` profiles the two timed steps, and `leaks --outputGraph` saves a memory graph at four of them. `memory-report.sh full` also turns on `MallocStackLogging` and adds `malloc_history` stacks; the logging itself then shows as up to 50 MB of `Performance Tool Data`. Everything stays in `/tmp/sharek-memory`; `resumen.txt` is the condensed report, also copied to the clipboard.
- `assets/icon/AppIcon.iconset` (128 pt and up only) and `AppIcon.icns` are rendered from the master `../assets/icon/AppIcon.svg`, whose dark rounded tile keeps macOS from drawing the icon shrunk onto a plate.
- Only Command Line Tools are installed: no `xcodebuild`, no asset catalogs, no storyboards. Everything UI is code.

## Layout

- `main.swift` picks the mode from the first argument: none runs the menu bar app, `--editor` the editor process, `--ocr` the text recognition helper.
- `App/` — menu-bar app shell: `AppDelegate` (hotkeys, quit notification, cleanup on terminate), `EditorProcess` (spawns and talks to the editor process), `IPC` (messages and framing shared by both processes), `Memory` (`MappedData`, the file-backed buffers every image lives in; returns freed malloc pages after captures and closed windows), Carbon global hotkeys (`HotKeyCenter`, no Accessibility permission needed; failures raise a toast), `StatusMenu` (settings toggles live here; while recording the icon turns into the red stop disc of `SwirlIcon.stopImage` and the menu starts with "Detener"), `MainMenu` (key equivalents routed through the responder chain to the page the editor window shows, `CapturePage` or `MediaPage`; capture items carry a `MenuAction` name and go to the coordinator, or from the editor process to the menu bar), `Settings` (UserDefaults), `LoginItem` (`SMAppService.mainApp`, registered once on first launch, toggled from the status menu), `SwirlIcon` (status-bar swirl drawn as vector at runtime, same geometry and colors as the master icon, and the recording stop disc with the proportions and red of the Linux tray).
- `Capture/` — ScreenCaptureKit stills (`ScreenCapturer`) as IOSurface-backed buffers (`SurfaceImage`), `CGWindowList` window frames for hover-detection (`WindowList`), frozen-screen region overlay with magnifier (`RegionSelector`, all CALayer compositing; its measuring mode is the screen ruler; `RegionLabel` writes the selection's pixels, aspect ratio and share of the screen), `ColorPicker` (system `NSColorSampler`, copies sRGB HEX), `ScrollingCapture` with `ScrollStitcher`, `PinWindow`/`PinManager` (floating always-on-top non-activating panels), `TextRecognizer` (Vision `RecognizeTextRequest`, result sheet, `Toast` HUD; both processes run it in a `--ocr` child), `CaptureCoordinator` (permission check, recording/scrolling sessions, delivery pipeline).
- `Record/` — `ScreenRecorder` (one `SCStream` per recording: MP4 through `SCRecordingOutput`, GIF through a stream output feeding `GIFEncoder`), `RecordingChrome` (region border + panel with an optional Manual button, both excluded from the capture filter), `GIFEncoder` (streaming GIF89a writer: per-frame median-cut palette, changed-rectangle frames with transparency, LZW).
- `Output/` — `CaptureDocument` (one per capture/tab: `EditorState` = base image + shapes, version counter), `Pixels` (every image in the pipeline: one 32-bit BGRA premultiplied buffer in a `Data`, top row first, with `PixelFormat` for size, row bytes and color space; crop, vImage scaling, nearest-neighbor copy into a bitmap (`blit`), color sampling; `BaseImage` holds a base image that can be packed), `PNGEncoder`, `AutoSave` (menu bar: the auto-saved file of each capture), `MediaCapture` (recorded MP4/GIF file; unsaved recordings live in the temp dir, wiped when the menu bar app launches), `ClipboardManager` (menu bar: an image promise, a file or several files per entry), `ImageWriter` (PNG through `PNGEncoder`, JPEG through ImageIO; DPI = 72 × scale so reopened files keep their Retina scale), `ImageOps` (cut-out, rotate, flip, frame), `History` (JSON index of saved files in Application Support; recorded on every successful write, dropped on discard/trash, pruned of missing files when the window opens), `HistoryWindowController` (thumbnail grid via `QLThumbnailGenerator`, rendered out of process and cached in an `NSCache`; reloads when the index file's modification date changes, polled every second).
- `Editor/` — the editor process: one dark (`darkAqua`) `NSWindow` for every capture and recording, with the Linux tab bar and layout; native window tabbing is off. `MenuBarLink` holds its end of the IPC link and its app delegate; `EditorClipboard` turns copies, edits, closes and pins into messages; `EditorManager` owns the tabs, the window, the history window and the count of pending file writes.
  - `Model` — `Shape` (single value type for every kind; geometry in canvas points, top-left origin), `ShapeStyle`, `Tool`, `StyleStore` (per-kind styles in UserDefaults, stored as drawn; `didChange` refreshes every open editor).
  - `EditorChrome` — `Theme` (the Linux palette, purpose colors for icons, `iconColors` for a tool's stroke and fill), `HintView`, `IconButton`, `CopyButton` (click copies; dragging it out offers PNG data and a file in `~/Library/Caches/ShareK/drag`).
  - `Icons` — `Icon` holds the path commands of `linux/crates/editor/src/icons.rs`, one per tool and action, and draws them as Slint's `Path` does: the 24 grid fitted to the icon side less the stroke width, butt caps, miter joins with limit 4. `IconPath` parses the commands those paths use (M, L, C, A, Z) and turns arcs into cubic curves. The app uses no SF Symbols. A Linux test (`icons::tests`) fails when a path here differs from the Linux one.
  - `EditorToolbar` — one row: Copy, file and OCR actions, undo/redo, the four tool groups, rotate/flip/frame, discard. Groups fold into a button with a menu, Effects first, then Text, Edit and Draw, as the window narrows; `fullWidth` is the unfolded width, also the minimum width a new editor opens at.
  - `OptionsPill` — floating options at the bottom: tool or shape name, color chips with `SwatchPopover` (titled with the color's label; 16 swatches, eyedropper, "Otro color…"), size pop-ups, shadow; compact (no name, no color labels) when it does not fit. `CapturePage.placeChrome` moves it left of the zoom control or lifts the zoom above it so they never overlap. `ZoomControl` — bottom-right zoom pill; `ImageFrame` — frame settings in UserDefaults and `FramePopover`.
  - `Geometry` — hit-testing, handles, text metrics; `ShapeRenderer` — one drawing path shared by the on-screen overlay and the export; `SoftShadow` — the shadow of a shape, the Linux algorithm line by line.
  - `EditorProbe` — answers `probe` messages (state, select a tab, click a tab, draw with a tool, undo, zoom, resize the window, render at another scale, minimize, restore, close a tab, close the shown tab as ⌘W does, pin the capture, close the pins, give the window another color space and measure again, write the shown frame as PNG) for `scripts/memory-check.py`; the menu bar never sends them.
  - `EditorTab` — what a tab keeps while another one is shown: a recording (`MediaCapture`) or a `CaptureTab` (the document, its undo history, the selection and the zoom and scroll position). Undo actions target the `CaptureTab`, which outlives the views.
  - `EditorWindowController` — the window: `TabBar` on top when there is more than one tab (layers only: title, a dot for unsaved changes, the accent line and the close button of the Linux bar) and under it the page of the shown tab. `EditorWindow` tells it when the window is about to leave the screen or comes back, and turns ⌘W into closing the shown tab; the red button closes every tab.
  - `CapturePage` — the views of the shown capture, built when its tab is selected and dropped when another one is: layout, snapshot-based undo (each commit registers the previous `EditorState`), zoom with auto-fit until the user zooms, rotate/flip/frame, save/copy/discard. `CanvasView` (document view: sets the scroll area to the image size and casts the shadow; it has no contents) sits inside `EditorScrollView`; `AnnotationView` is an overlay sibling of the clip view sized to the viewport, rendering the base image and the shapes through a document→view transform into the frames of `FrameBuffers` and owning all mouse/keyboard interaction, including the OCR-area drag (`selectingText`) and the eyedropper (`picking`).
  - `MediaPage` — the page of a recording: the action bar of the Linux editor (Copy, save, save as, open in the default player, show in Finder, discard) over an AVKit player or an animated GIF; the window subtitle carries format, size and file size.

## Processes and IPC

- The menu bar process keeps hotkeys, the status menu, region selection, captures, recordings, scrolling capture, pins, toasts and the clipboard. It starts the editor process on demand with `Process` (`ShareK --editor`, same executable) and talks to it over the child's stdin and stdout; the editor moves its stdout to a private descriptor and points fd 1 at `/dev/null`, so a stray print cannot corrupt the stream. A message is a u32 length, a JSON header and a u64-length payload (`IPC.swift`), the same framing as Linux. SIGPIPE is ignored in every mode.
- Images cross as raw pixels (`PixelFormat`: size, row bytes, color space name or ICC profile; always 32-bit BGRA premultiplied), so the editor keeps the payload itself as the capture's bitmap. Copies and edits come back as PNG with the DPI of the capture scale.
- The editor offers to exit with `exiting(received:)` when it has no window and no file write pending, once per received count; the menu bar answers `exitAccepted` only if it has sent nothing since, and from then on sends that process nothing else, so the next capture starts a new editor process. It still handles every message the old process sends until its stdout reaches EOF, and accepts any later offer from it at once, so a process that got busy again is never orphaned. The editor exits on `exitAccepted` only while idle with an empty outbox, and otherwise offers again once it is. Its own "Historial…" goes through the menu bar like every other window it opens, so the menu bar's count covers it.
- A frame whose header exceeds 1 MiB or whose payload exceeds 2 GiB is refused by the sender and not counted. A color space with a name travels by name; only unnamed ones carry their ICC profile.
- Messages from the editor leave in the order they were queued: `sendLater` reserves a slot while a PNG is encoded off the main thread, so a copy is never overtaken by the discard or close that follows it. Closing a tab with an edit still waiting for the 600 ms clipboard debounce sends that edit first.
- Clipboard ids: the menu bar numbers captures from 1; tabs and history copies an editor process starts itself take ids from `1 << 48 | pid << 24`, so two editor processes never reuse one. The menu bar announces the owning id (`clipboardOwner`) after every clipboard change; the editor sends `changed` only for the owner.
- Activation: before handing the editor a window to show, the menu bar activates itself (it has the user's hotkey or click); the editor sends `activate` once its window is up and the menu bar yields activation to it (`yieldActivation(to:)`, `activate(from:)`). Capture items in the editor's main menu yield activation to the menu bar before forwarding, so the region overlay gets the keyboard.
- The editor process is `.regular` (Dock and ⌘Tab) for its whole life; the menu bar process stays `.accessory`. ⌘Q in the editor quits ShareK through the menu bar; quitting the editor from the Dock closes its windows and ends only that process. The editor terminates when its stdin reaches EOF.
- Both processes write `history.json`, so every change takes an `flock` on `history.json.lock`, reads the file, applies itself and writes it back atomically.
- Auto-save: the menu bar writes every capture's file with the PNG it puts on the clipboard (`AutoSave`), and passes the path in `open` so the editor shows the capture as saved there. It renames the file into place with `renamex_np(RENAME_EXCL)` (a move after an existence check on volumes that lack it), so a save the editor made first is never overwritten, and reserves the name until it lands, so two captures in the same second never share it. Discarding the capture sends `trash`: the menu bar moves the file to the Trash, or does it when the write lands. The editor writes its own saves on one serial queue.
- Text recognition (hotkey, pins and the editor's result sheet) runs Vision in a `ShareK --ocr` child that reads PNG on stdin and writes the text on stdout, so only that child runs Vision and loads its models.

## Mechanisms and footguns

- Clipboard (menu bar): an image is offered as a lazy PNG promise (`ImageProvider`), PNG only, as on Linux, so it is on the clipboard the moment the capture ends. A capture's PNG is encoded in the background right away (once, shared with the auto-save) and the raw image is dropped; a paste that arrives first encodes it on the spot. Copies and edits from the editor arrive already encoded. `flush()` on terminate rewrites the current entry as PNG data. `ClipboardManager` snapshots the user's prior clipboard and keeps a history of up to five entries so "discard" restores the previous capture or the original clipboard — only if the pasteboard `changeCount` still matches ours. Closing a capture's tab drops it from that history (`release`): if it is still on the clipboard it is rewritten as PNG data, which frees the promise and its PNG copy; with no capture left the original-clipboard snapshot goes too. macOS never tells the owner when another app replaces the clipboard (`pasteboardFinishedWithDataProvider` does not fire), so only `release` frees an entry whose tab is gone.
- One copy per capture: bitmaps are drawn straight into the `Data` that becomes the `Pixels` (`Pixels.render`), crops copy rows, and nothing goes through `CGContext.makeImage()` plus `CGDataProvider.data`, which cost a full copy each. A `CGImage` made from `Pixels` shares its buffer and is made per use, never kept.
- Image data stays out of anonymous memory. Every large buffer ShareK allocates (pixels, packed pixels, PNGs, IPC payloads, the view copy, the scene bitmap) is a mapping made by `MappedData` and unmapped as soon as its `Data` is released. From 1 MiB up it is a `MAP_SHARED` mapping of an unlinked file in the temp directory: `phys_footprint` (Activity Monitor's Memory, `footprint`) counts a task's anonymous pages and none of its file-backed ones, and under pressure the kernel writes those pages to the file; it does not compress or swap them. The file is sparse and has no name: it takes disk only for the pages written and goes away with the mapping or the process, crash included. Below 1 MiB, when the volume lacks the buffer's size plus 1 GiB of free space, or when the file cannot be made, the mapping is anonymous. `MAP_PRIVATE` would defeat it, since a written page of a private file mapping becomes anonymous. What is left in the editor's footprint is AppKit, the chrome's backing stores and the blur and pixelate results Core Image returns (`EffectCache`, anonymous, sized by the shape); the frame the overlay shows is a mapping too. A `Data(bytesNoCopy:)` of 14 bytes or less is stored inline: Foundation copies the bytes and runs the deallocator at once, so a pointer into a mapping outlives `make` only for larger buffers, and `Pixels.drawable` refuses anything under 2×2.
- Stills are IOSurface-backed `CVPixelBuffer`s in Display P3 from `SCScreenshotManager.captureSampleBuffer`, awaited on the main actor: the content filter is main-actor state, and Swift 6 refuses to send it to a nonisolated function. The frozen screens are shown as layer contents directly, tagged with `IOSurfaceColorSpace` so Core Animation matches their colors. The selection is copied out of the surface; selecting a whole screen hands the surface itself on. A pin keeps its `Pixels` and shows them through `FrameBuffers` like the editor's frame, with linear minification, since mipmaps need a separate texture.
- `PNGEncoder` writes PNG row by row over zlib, like the Linux encoder: RGB when the image is opaque, adaptive row filters, the color profile (`sRGB` or `iCCP`) and pHYs DPI; level 1 for captures, the clipboard and drags, the default level for saves from the editor. ImageIO's PNG writer converts the whole bitmap first. JPEG (Save As) still goes through ImageIO.
- The editor draws like the Linux one. The overlay has no AppKit backing store (`wantsUpdateLayer`): `updateLayer` renders each frame through a `CGContext` into a file-mapped buffer of its own (`FrameBuffers` over `MappedFrame`: 8-bit BGRA, viewport-sized at backing scale, rows padded to 64 bytes) and sets a `CGImage` over that buffer as the layer's contents. The base image reaches the frame by pixel copy (`Pixels.blit`, nearest-neighbor): straight from the base when an image pixel covers a screen pixel or more, else from a view-sized copy scaled with vImage and keyed by the area and its size. Three frames rotate while frames follow each other, so the one being written left the screen two frames before, and the spares go half a second after the last frame. A suspended overlay renders nothing; if AppKit asks it for a frame, it asks `EditorManager` to recheck visibility. The drag preview is scaled with vImage too.
- The frame costs the editor no memory only while the window's color space is the frame's. Core Animation hands a `CGImage` whose color space equals the window's (`NSWindow.colorSpace`) to the window server as it is, pages of the mapped file included; with any other color space it first converts the image through Core Graphics, which leaves one copy in Core Animation's shared memory and another in malloc, twice the frame. So `AnnotationView.tagWindow` sets the window's color space to the capture's before the first frame and whenever the base changes, and the window server matches the whole window to the display. The frame stays in the capture's color space, so nothing is converted here either. `FrameBuffers` checks that once per process, right after its first frame: it shows a 2048×2048 mapped image of its own in a 1 pt sublayer and reads the footprint before and after the commit. If the footprint grew by more than half that image, Core Animation copies mapped frames on this system, and every `FrameBuffers` from then on draws into IOSurfaces tagged with their color space (`SurfaceImage`), which cost the frame once and are shown without conversion. An IOSurface the window server has replaced stays in use for some frames: waiting for `IOSurfaceIsInUse` to clear before reusing a spare allocates a surface per frame of a drag.
- No large image goes through Core Graphics in a pixel format or color space other than its own, and none is drawn in a view's `draw(_:)`. AppKit records `draw(_:)` in a display list and replays it into a backing store the size of the view, half-float (8 bytes per pixel) on a wide-gamut display, held in a private content layer where `layer.contents = nil` does not reach it. For the same reason the wide views of the chrome have no `draw(_:)`: the toolbar's border and separators are 1 pt layer-backed subviews, and the tab bar is made of layers. Core Graphics keeps a converted copy of each image it draws that way (`img_data_lock`), long after the `CGImage` is released: one view-sized block per call. A draw in the image's own format and color space, like the export, allocates nothing. `scripts/memory-report.sh` shows both as `CA Whippet Drawable` surfaces and `create_image_data_handle` blocks.
- Blur and pixelate read pixels from the base image only and are cached per shape in `EffectCache`. The highlight draws the base under what is already in its rectangle (`.destinationOver`) and multiplies the result by its color, so it tints shapes the same in the transparent overlay and in the export.
- `Pixels.scaled` hands vImage a temp buffer from `MappedScratch`. Left to allocate its own, `vImageScale_ARGB8888` takes tens of MB from malloc for a full-screen capture, and libmalloc keeps them dirty after the call.
- Shadows are computed here, not by Core Graphics: `ShapeRenderer.shadowed` draws the shape into a half-resolution layer in a reusable mapped buffer, `SoftShadow` blurs its coverage with three box passes and darkens the frame's pixels under it, then the shape is drawn on top. A transparency layer with `setShadow` makes Core Graphics allocate a buffer the size of the shape on every draw; libmalloc keeps those blocks dirty after they are freed, and with sizes that change on every frame of a drag they add up to hundreds of MB. `SoftShadowTests` and the Linux test `the_shadow_gives_the_values_the_macos_editor_is_tested_against` pin both ports to the same numbers.
- The window gives up its frame and its chrome before it leaves the screen, never after: the window server keeps the last contents of a window that is hidden, and a change made afterwards is not applied until the window is back. So `EditorWindow` suspends the page in `order(.out)` and `close`, and the controller in `windowWillMiniaturize` and when the window becomes fully covered. `suspend` ends with `CATransaction.flush()`. It removes the toolbar, the options pill, the zoom control and the hint (`Chrome`), which `resume` builds again once the window is visible; the scroll view is pinned to the page, not to the toolbar, so its viewport does not move meanwhile.
- While a shape is dragged or a text is edited, the overlay keeps a frame-sized bitmap (`Pixels.drawable`: a mapped buffer with a `CGContext` over it), in the frame's color space, of the base and the settled shapes (everything below the first dragged, edited or selected shape), keyed by the document transform, view size, backing scale and base, and compared by `ShapeRenderer.fingerprints`. Each frame copies it and renders only the live shapes; new settled shapes are drawn into it, any other change rebuilds it. Outside an interaction it is dropped.
- Closing a tab purges it before anything else can keep it alive: its page closes (text being edited is committed, the popovers are dismissed, the frame and the scene bitmap go), the tab leaves `EditorManager`, and then its undo history and the document's image (`CaptureDocument.discardContents`) are dropped. The color and frame popovers live in statics and are cleared on `popoverDidClose` (`PopoverCloser`); a closed popover kept in a static can keep its page alive. Closing the last tab closes the window, and closing the window closes every tab. A page that closes ends the drag in progress first (`AnnotationView.endDrag`), so a shape half drawn when a new capture arrives keeps its undo step. While a sheet hangs from the window (Save as, recognized text) the shown tab stays: a capture that arrives is added behind it, and the tab cannot be switched or closed, because the sheet's completion belongs to that page.
- Only the shown tab has views. Selecting another tab closes the page (`CapturePage.close` stores the selection and the zoom and scroll position in the `CaptureTab`) and builds the page of the new one, so a tab that is not shown costs its document and nothing else, and `CaptureDocument.isHidden` packs its base images. While the window is covered, minimized or on another Space the page stays but holds no frame, view copy, scene bitmap, blur/pixelate cache or chrome: `updateVisibility` suspends it and resumes it once the window is not occluded; an occlusion change away from visible suspends at once. `BaseImage` compresses its raw pixels with LZFSE once, straight from the buffer, and frees them, so a hidden capture takes a fraction of its raw size on the temp volume; it decompresses them again on first use. An image that LZFSE cannot shrink stays raw and is not tried again. Packing runs on one serial queue, so a burst of captures never compresses several images at once. A capture opened from the menu bar keeps the IPC payload itself as its pixels. Base images that only the undo history still holds (before a crop, rotate, flip or frame) are packed as soon as the document moves past them. The export is never cached; each copy, save or eyedropper pick renders it.
- `ClipboardManager.forgetIfReplaced` drops the capture history, the original-clipboard snapshot and the current promise once another app owns the pasteboard; it runs at the start of every capture flow and on every clipboard sync with the editor.
- Every ShareK process runs with `MallocSpaceEfficient=1`. malloc reads it only at launch. LaunchServices sets it for the menu bar process from `LSEnvironment` in `Info.plist` (`install.sh` re-registers the bundle so a new `Info.plist` is read), and the editor and OCR children inherit it; when one of those children lacks it, `main.swift` sets it and executes itself again. The menu bar process must never re-execute itself: `exec` gives the process a new audit token, and Control Center then refuses the status item of a process LaunchServices launched ("scene activation failed"), so the icon never shows. A menu bar process started from a shell runs without the variable. Without it the allocator of macOS 26 keeps every freed large block dirty in the footprint for as long as the system has memory to spare (`malloc_zone_pressure_relief` does not return them; drawing large shapes, an export or a pin leave 10 MB behind) and spreads small objects over twice the pages their live bytes need. `MallocAggressiveMadvise`, `MallocSecureAllocator=0` and `MallocNanoZone=0` change nothing, and `MallocLargeCache=0` frees only the large blocks.
- `Memory.releaseSoon` runs `malloc_zone_pressure_relief` 2 s after every capture flow, recording, closed or switched tab, suspended page, packed base image, encoded or written capture PNG, PNG sent by the editor, rebuilt view copy, dropped scene bitmap, closed pin and the last frame of a burst. The editor process returns everything when it exits.
- The title bar sets the floor of the editor's heap: on macOS 26 the standard window buttons are drawn through SwiftUI, so any titled window loads SwiftUI, AttributeGraph and the SF Symbols name tables, about 2 MB of heap and type metadata.
- Text shapes size themselves (`TextMetrics.fit`). While editing, an `EditingTextView` inside the canvas takes input with clear text, caret and selection; the overlay keeps drawing the shape and draws the caret and selection from `firstRect(forCharacterRange:)`. The text view has its own `UndoManager` per edit; its ⌘Z and ⇧⌘Z go to the document once the text is back where it started, or, for redo, when nothing was typed. After an option changes, `restoreFocus` returns the first responder to the text view or the overlay. A double click on a text edits it with any tool.
- Rotate, flip and frame rewrite the base image and move the shapes, like crop, so they undo as one step; text and pasted images keep their size and stay upright around their new center. The frame is baked into the base.
- ImageIO's GIF destination buffers every frame until finalize (~1.6 GB for 300 frames of 900×560), hence the hand-written `GIFEncoder`. GIFs record at 1× point size and 15 fps; ScreenCaptureKit only delivers frames when content changes, so delays come from presentation timestamps.
- Recording: a stop that does not finish in 15 s closes the session with a toast. Quitting during a recording deletes its partial file.
- Scrolling capture: frames exclude every ShareK window, pins included. The first frame and every frame after an automatic scroll wait until two captures 60 ms apart match (up to 1.5 s). Automatic scrolling warps the cursor to the region center once at the start and then posts one pixel-unit `CGEvent` scroll wheel per step where the cursor is, sized from how far the previous one moved (aiming at 40 % of the region); a warp also suppresses hardware mouse events for a moment, so warping on every step locks the user out of the mouse. A scroll is posted only while `NSEvent.mouseLocation` is inside the region. A step without overlap is scrolled back and retried smaller, and after four misses, when the cursor leaves the region, with the Manual button or without Accessibility permission (bound to the code signature) the session is manual: frames every 80 ms, "Desplázate", or "Más despacio" while they do not overlap. `ScrollStitcher` hashes only the columns that move, matches 16-row windows, requires 90 % agreement over the overlap, treats 97 %-identical frames as unchanged and keeps the fixed footer below the last moving row out of every seam.
- `NSColor.withAlphaComponent` on a dynamic system color resolves it against the drawing appearance current at that call, so layer colors are built and converted inside `effectiveAppearance.performAsCurrentDrawingAppearance` or `updateLayer`; built outside, a light window gets dark-mode colors.
- The overlay sits at `.screenSaver` level; `Toast` is one level above so it stays visible over the ruler. Errors are toasts; only the missing Screen Recording permission opens an alert.
- Screen Recording permission (TCC) is bound to the code signature. Ad-hoc signing (`-`) changes identity on every build, so the permission must be re-granted after each rebuild; the `Nico Local` identity keeps it.
- Default hotkeys ⌘⇧3/4/5 (capture), ⌃⇧6/7 (record MP4/GIF), ⌃⇧8 (scrolling capture), ⌃⇧9 (pin region), ⌃⇧0 (OCR to clipboard), ⌃⇧1 (color picker), ⌃⇧2 (ruler), ⌃⇧H (history). The same key stops a running recording or scrolling session; the color picker and the ruler are ignored meanwhile. `RegisterEventHotKey` succeeds for ⌘⇧3/4/5 even while the macOS screenshot shortcuts are enabled, but the system wins: they must be turned off in System Settings → Keyboard → Keyboard Shortcuts → Screenshots.
- The login item is keyed by bundle identifier and path in the Background Task Management database (`sfltool dumpbtm`), so reinstalling over `~/Applications/ShareK.app` keeps it.
